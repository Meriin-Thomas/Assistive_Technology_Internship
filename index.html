MSP430 Familiarization

We received the microcontroller that we would be using for the project: the MSP EXP430 FR4133 from Texas Instruments. We had never worked with this board before, so we were encouraged to begin with small programs to familiarize ourselves with it.

The idea was to start simple, such as reading inputs from onboard push buttons and controlling LEDs in response. From there, we could gradually move towards more advanced tasks such as using the LCD display, reading sensor data, and eventually displaying muscle activity data for our project.

We spent some time researching the board and understanding its features. The MSP-EXP430FR4133 is built around the MSP430FR4133, a 16-bit ultra-low-power microcontroller that uses FRAM technology, making it a good choice for energy-efficient embedded applications.

We learned that the board follows the 20-pin LaunchPad standard, allowing compatibility with BoosterPack expansion modules. It also includes an onboard eZ-FET debugger with EnergyTrace support for power monitoring and debugging.

Based on the pin map and user guide, we found that the board provides 10 analog-capable channels (A0–A9) for ADC operations and sensor interfacing, while also exposing multiple configurable digital GPIO pins through ports such as P1.x, P2.x, P5.x, and P8.x. Since the MSP430 architecture uses multiplexed pins, many pins can function as analog channels, digital GPIO, timers, or communication peripherals depending on software configuration.

We also learned that the board uses port-based access for interacting with peripherals and pins. Inputs and outputs are organized into ports, allowing pin states and peripheral functions to be configured through software using port registers.

Multiple communication interfaces are supported by the board, including UART for serial communication and debugging, I²C for communicating with sensors and peripheral devices, and SPI for higher-speed communication with external modules. These interfaces are mapped onto shared pins and can be configured depending on application requirements.

Although the board supports several wired communication protocols, we found that it does not include built-in wireless hardware such as Wi-Fi or Bluetooth. Any wireless functionality would therefore need additional external modules connected through interfaces such as UART, SPI, or I²C.

We familiarized ourselves with the onboard peripherals available for testing and interaction, including:

  • Segmented LCD display
  • Two push buttons
  • Two onboard LEDs
  • USB backchannel UART communication

The segmented LCD was especially interesting because it allows output display without requiring external hardware. We also learned that the USB backchannel UART could be used for debugging and serial communication with a computer.

LED Control and Debugging Lessons

After the button counter program, I wrote a simple program to toggle an LED using a switch input.

During testing, I became confused when the controller would not continue running after unplugging and reconnecting the board, which I was accustomed to doing in Arduino.

Eventually, I realized the issue was related to how active debugging sessions work in Code Composer Studio rather than a problem with the code itself.

  • When a debug session is launched, Code Composer Studio takes control of the microcontroller through the onboard debugger.
  • While debugging is active, the IDE controls execution state, memory access, breakpoints, and program flow.
  • If the board is unplugged while the debugger still has control, the microcontroller may not properly return to standalone execution and can appear unresponsive or stuck.
  • The correct workflow is to terminate the debug session using the red square Terminate button before disconnecting power or unplugging the board.
  • After terminating debugging correctly, the flashed program ran normally when I powered it again.

Day 6 More LCD Programs and Analog Data Display

Memory Optimization Experiments

While reviewing yesterday’s LCD display code, I noticed that I had imported libraries such as <string.h> and <stdint.h>. Initially, I assumed that removing unnecessary imports would reduce memory usage, so I experimented with simplifying the code.

The original implementation used:

  • 448 / 15,232 bytes FRAM (~3%)

After modifying the implementation, the program size became:

  • 444 / 15,232 bytes FRAM (~3%)

At first, I assumed that removing unused headers was responsible for the size reduction. However, after investigating further, I learned that unused headers themselves do not significantly affect compiled size because modern compilers remove unused definitions during compilation and linking.

The actual difference came from replacing a hardcoded numeric constant with a character literal. In one part of the LCD character mapping logic, I changed:

  • c - 65

to:

  • c - 'A'

Since the MSP430 is a 16-bit architecture, using the integer literal 65 caused additional instructions to be generated for type conversion and data handling. Using the character literal 'A' allowed the compiler to generate more efficient instructions because both operands were treated as matching character-sized values.

The savings were only four bytes, but it was interesting to realize how small implementation decisions can affect compiled size in embedded systems. Every byte matters, especially since future programs may become much larger and eventually could need enough room for embedded ML functionality.

I experimented further with the LCD by making a program where button presses changed the displayed words and cycled through a list of strings. This consumed around 7% FRAM.

After that, I implemented scrolling text, where characters shifted one position at a time from right to left, allowing sentences longer than the display width to move across the screen. Surprisingly, this implementation required only around 5% FRAM, even though I initially expected animation logic to be more memory intensive.

Looking deeper into the compiled code made me realize why the button-controlled version occupied more memory. The increased memory usage came from several factors:

  • Additional lowercase character support introduced extra conditional checks, arithmetic operations, array indexing, and bit manipulation instructions.
  • Using an array of string pointers for word selection required additional storage for pointer tables and extra instructions for accessing the correct string.
  • Button handling itself added significant overhead through GPIO configuration, input polling, debouncing logic, conditional branching, and delay routines.

This was interesting because it highlighted that in embedded systems, hardware interaction and control logic can sometimes consume more memory than display algorithms or mathematical operations.

Day 7 Sensor Data Reading and Display

June 4, 2026

LCD Driver Experiments and Memory Optimization

Based on advice from others, I tried importing additional files from the MSP430 demo projects into my own project, including hal_LCD.c, hal_LCD.h, and main.h, while also including hal_LCD.h in my code.

The display suddenly worked much better. Numbers became bright, clear, and correctly rendered. However, I noticed it consumed around 8% FRAM.

This was especially interesting because earlier versions of my code already displayed the correct numerical values, but the LCD output itself looked strange. Segments appeared faint, characters looked distorted, and parts of digits seemed to bleed into neighboring segments.

After investigating further, my current understanding is that the issue was likely caused by incomplete or incorrect LCD peripheral configuration rather than problems with the displayed data itself.

The MSP430FR4133 LaunchPad uses a multiplexed segmented LCD, where multiple physical pins share responsibility for driving different display segments depending on timing and common-line configuration. If LCD control registers, multiplexing settings, or segment mappings are not configured correctly, unwanted segments can partially activate, producing ghosting or segment bleeding effects.

The imported hal_LCD.c implementation appears to solve this by correctly configuring the LCD peripheral for the specific segmented display used on the board. This likely included:

  • Proper multiplexing and COM-line timing configuration
  • Correct charge pump and LCD voltage settings for display contrast
  • Board-specific segment mapping for the FH-1138P display
  • Safer segment updates using masking operations instead of overwriting memory directly

In earlier programs, I was directly manipulating LCD memory registers using raw memory access macros. While functional, this approach may have unintentionally altered neighboring segments or configuration bits, contributing to the display artifacts I observed.

The tradeoff for this improved reliability was memory usage. Since the HAL implementation includes lookup tables, mapping logic, helper functions, and support for many display symbols and characters, importing it increased FRAM consumption considerably.

Shreyas managed to make a working LCD code without importing those additional files and only included driverlib.h. Surprisingly, despite seeming much larger and more feature-rich, this implementation used only around 3% FRAM.

Initially this seemed counterintuitive, but after investigating further, I learned that the increase in memory usage mostly came from importing the large hal_LCD.c implementation rather than from the visible code itself.

The standard LCD HAL implementation includes many additional utilities such as scrolling support, symbol mappings, lookup tables, and helper functions. Depending on optimization settings, importing these files can pull in significantly more code than expected.

In contrast, the smaller implementation benefited from compiler optimizations such as dead code elimination. Even though driverlib.h contains many functions, the compiler only included the functions that were actually used while removing unused code automatically.

This was an interesting reminder that source code size and compiled size are not always related in obvious ways in embedded systems.

MYOWARE 2.0 Familiarization

We finally received the MYOWARE 2.0 Muscle Sensor, which would play a major role in our project.

Serial Console Debugging

We returned to testing the MYOWARE sensor, but once again encountered the same issue as before. The sensor initially produced good readings and then suddenly stopped working. We checked the jumper wires, verified connections using a multimeter, and tried replacing components, but could not identify the cause. Since the sensor was no longer producing reliable readings, it was also difficult to determine whether the software itself was functioning correctly.

We discussed the issue with Aravind Sir, who suggested using the terminal for easy debugging instead of using the LCD display. Although I had previously attempted to use UART communication without success, this seemed like a good opportunity to revisit it.

Our first goal was simply to print a "Hello" message to the terminal. After discovering that the serial terminal interface in Code Composer Studio is called the Serial Console, I configured the baud rate and attempted communication. The result was unreadable gibberish rather than the expected text.

Aravind Sir suggested that the problem might be related to the clock configuration. To investigate this, we connected a logic analyser and observed the transmitted UART signals directly. The analyser showed that data was indeed being transmitted correctly, but the clock frequency was not what we expected.

Although the code had been configured for a 1 MHz clock, measurements showed the actual frequency was approximately 1.45 MHz. Since UART communication relies heavily on accurate timing, this discrepancy explained why the serial console could not decode the transmitted data correctly. Aravind Sir also lent us an external USB-to-serial converter to make sure the issue was not being caused by the communication hardware. The cable we had been using could serve multiple purposes, so we wanted to eliminate that variable. Unfortunately, the output was still gibberish, which pointed us back towards investigating the clock configuration.

Using the measured clock frequency, I adjusted the code to compensate for the timing error. This allowed the "Hello" message to appear correctly in the serial console, confirming that the clock mismatch was the root cause.

Rather than relying on this workaround, I spent some time studying the MSP430 clock system and reading the datasheet in greater detail. This led me to learn about the Frequency Locked Loop (FLL), which can continuously calibrate the Digitally Controlled Oscillator (DCO) using a more accurate reference clock source.

The FLL is disabled by default, hence we saw DCO drift. This was not apparent before as tasks such as LCD updates, sensor readings, SPI communication, and I²C communication do not require extremely precise timing. As long as the clock is reasonably close to the expected frequency, these peripherals continue to function correctly. UART communication, however, requires both the transmitter and receiver to agree closely on the timing of each bit. The DCO drift that had gone unnoticed in previous projects was large enough to push the baud rate outside acceptable limits, causing the serial console to display corrupted data. After enabling the FLL and configuring the system clock to operate at 8 MHz, UART communication began working reliably without any special adjustments. The DCO was now automatically corrected using the reference clock, keeping the timing error within acceptable limits for serial communication.

Further investigation into the MYOWARE ENV LED issue is still required, but at least we solved this mysery today!

Day 12 Solving the MYOWARE Mystery and Event Preparation

June 11, 2026

The ENV LED Issue

With UART communication working reliably, I decided to display the MYOWARE ADC readings through the serial console. The readings appeared to work initially, but the same issue from previous days soon returned: the ENV indicator LED remained permanently lit, even when no muscle activity was present.

While researching possible causes, I came across information suggesting that electrical noise from charging circuits could interfere with sEMG measurements. At the time, my laptop was connected to its charger. To test the theory, I switched off the charger and immediately noticed that the ENV LED turned off. Reconnecting the charger caused the issue to reappear. When charge was low, I would power the laptop and continue as usual, which explained why the sensor would seem to suddenly stop working.

This revealed that the sensor was not detecting muscle activity at the time, but mains interference introduced through the charging system. Since my laptop charger does not have an earth connection, the laptop and user effectively float at an AC potential relative to ground. The body then acts like an antenna, allowing 50 Hz mains noise to couple into the MYOWARE electrodes. The interference was strong enough to be interpreted by the sensor as continuous muscle activity, causing the ENV LED to remain illuminated. The solution was simply to perform measurements while running on battery power rather than while charging.

Investigating this issue also provided some insight into why biomedical instruments such as EMG and ECG systems are often battery-powered or electrically isolated. Even relatively small amounts of mains interference can significantly affect bioelectrical measurements.

Confirming sEMG Values

Although the previous day's code appeared to be working correctly, I was still uncertain about the accuracy of the calculated sEMG values. Most sources described surface EMG signals as being in the 0 - 10 millivolt range, and I wanted to verify whether the values being reported by the code were correct.

To investigate this, I modified the program to display both the raw ADC reading and the calculated sEMG voltage simultaneously. I also compared the calculation method against another implementation that I trusted, which used an ESP microcontroller. The underlying logic was identical, increasing my confidence in the approach.

I then performed several validation tests by disconnecting the MYOWARE sensor and directly applying known voltages to the ADC input pin. Connecting the pin to ground produced an ADC reading of 0 and an sEMG value of 0 mV. Connecting it to 3.3 V produced an ADC reading of 1022 and a calculated value of approximately 16.48 mV, which is extremely close to the theoretical maximum of 1023 counts and 16.5 mV.

These tests confirmed that both the ADC measurements and the conversion calculations were functioning correctly. The ADC values were being measured directly by the microcontroller, while the sEMG values were obtained by reversing the amplification applied internally by the MYOWARE sensor using the gain specified in the documentation.

After confirming the calculations, we tested the sensor on Anupama Chechi. Small movements produced relatively low readings, normal hand grips generated values approaching 10 mV, and very strong contractions reached approximately 14.65 mV. We were unable to produce values significantly higher than this during testing.

To visualize the measurements more effectively, we also plotted the serial output using Better Serial Plotter and observed the changes in muscle activity over time.

During testing, the dedicated UART port on the WaveShare board unexpectedly stopped functioning and produced a "Set Address Failed (Code 43)" error. Since our previous work with the WaveShare had relied on this port, the issue initially raised concerns that the board might have been damaged.

We also investigated possible causes of the UART failure. We suspect damage to the USB-to-UART bridge chip, the CH343P. The fact that the native USB interface works suggests that the ESP32-S3 is still healthy and that the problem may be isolated to the UART circuitry.

Improving SD Card Data Logging

Alongside the WaveShare experiments, work continued on improving the SD card data logging system. Anupama Chechi was modifying the logging code to reduce storage waste. In my earlier implementation, each ADC reading was written to an entire 512-byte sector, leaving most of the sector unused. While this simplified data retrieval, it was highly inefficient in terms of storage utilisation.

The updated approach allows data to be written more efficiently by using partial sector writes and flushing data as required. The code can also detect the SD card type and automatically adjust its addressing method depending on whether the card uses sector-based or byte-based addressing.

During testing, I noticed that the SD card was being reformatted repeatedly even though it had already been formatted as FAT32. Some of the test programs were creating new file systems during execution, which risked overwriting existing data. This became apparent when the card unexpectedly reported that it was nearly full despite containing very little user data. After discussing the issue with the team, we agreed that unnecessary formatting should be avoided to prevent accidental data loss.

An interesting breakthrough occurred when we successfully wrote raw data directly into sectors belonging to an existing text file whose starting location was already known. This demonstrated that data could potentially be logged directly into files while still taking advantage of low-level sector access techniques.

I also carried out some experiments with large text files to better understand storage and software limitations. During testing, Microsoft Notepad struggled to open files larger than a few tens of megabytes and was unable to reliably handle some of the larger files I created. This is largely because traditional text editors such as Notepad attempt to load the entire file into memory at once, making them inefficient for very large datasets.

In contrast, Visual Studio Code was able to open files approaching 1 GB in size with much less difficulty. Modern editors often use more efficient techniques such as incremental loading, virtualization, and optimized memory management, allowing them to work with significantly larger files. I also learned that there are specialized tools designed specifically for viewing massive text files, such as Large Text File Viewer (LTF Viewer), EmEditor, and LogExpert, which can handle files several gigabytes in size without loading the entire contents into memory.

These experiments provided useful insight into how future sensor datasets could be stored, viewed, and analyzed. As logging durations increase and data volumes grow, selecting appropriate software tools becomes just as important as designing efficient storage methods on the embedded system itself.
